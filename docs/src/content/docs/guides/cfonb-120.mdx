CFONB 120 is the French bank statement format (_relevé de compte_, also known as ETEBAC 3): one record of 120
characters per line, its first two characters being the record code.

| Record | Parsed into                                                        | Reached with                  |
| ------ | ------------------------------------------------------------------ | ----------------------------- |
| `01`   | [`Balance`](/reference/cfonb-120-objects/#balance)                 | `$statement->getOldBalance()` |
| `04`   | [`Operation`](/reference/cfonb-120-objects/#operation)             | `$statement->getOperations()` |
| `05`   | [`OperationDetail`](/reference/cfonb-120-objects/#operationdetail) | `$operation->getDetails()`    |
| `07`   | [`Balance`](/reference/cfonb-120-objects/#balance)                 | `$statement->getNewBalance()` |

## Reading a file

`Cfonb120Reader::parse()` takes the contents of the file, not its path, and returns a list of
[`Statement`](/reference/cfonb-120-objects/#statement):

```php
use Silarhi\Cfonb\Cfonb120Reader;

$reader = new Cfonb120Reader();
$content = file_get_contents('/path/to/cfonb120-file.txt');

foreach ($reader->parse($content) as $statement) {
    // Process each statement
    echo "Statement date: " . $statement->getNewBalance()->getDate()->format('Y-m-d') . "\n";
}
```

## How statements are built

The reader goes through the lines in order:

- an old balance line (`01`) opens a statement.
- an operation line (`04`) is added to the open statement.
- a detail line (`05`) is added to the last operation read.
- a new balance line (`07`) closes the open statement, which is then added to the list: the next operation line needs a
  new `01` line.
- an empty line is ignored; a line of spaces or tabs throws a `ParseException`.

Any other order throws a `ParseException`, in strict and non-strict mode alike: a `07` line, an operation or a detail
line with no open statement, a `01` line while a statement is still open, a statement still open at the end of the file
(a truncated file).

:::note[Since 6.5]
6.4 did not check this order: it paired the balance lines by their position in the file, so records out of order
produced wrong statements silently instead of throwing.
:::

<Example name="cfonb120-sequence" />

So every statement returned has both balances: `hasOldBalance()` and `hasNewBalance()` are always `true` on them, and
`getOldBalance()` and `getNewBalance()` never throw. A bank usually sends one statement per account and per day: a file
can hold several days and several accounts, in the order the bank wrote them.

The reader checks the order of the records, not that they add up: call `$statement->validate()` (since 6.6) to check
that the operations belong to the account of the statement and that the new balance is the old balance plus the
operations. See [checking the consistency of a file](/guides/troubleshooting/#checking-the-consistency-of-a-file).

## Operations

<Example name="cfonb120-operation" />

- `getCode()` is the operation code of the CFONB, `B1` here: [operation codes](/reference/operation-codes/) gives its
  label.
- `getDate()` is the operation date, `getValueDate()` the value date.
- Fields left blank in the file are `null` for the nullable getters (`getRejectCode()`, `getBankOperationReference()`
  above); the others throw a `ParseException` when blank, except the reference in
  [non-strict mode](#strict-mode-default-vs-non-strict-mode).
- `getDetails()` lists the `05` lines of the operation, in order: their `getQualifier()` (`LIB` for an extra label line)
  tells what `getAdditionalInformations()` holds.

All the fields, with their positions in the line: [CFONB 120 objects](/reference/cfonb-120-objects/).

```php
foreach ($reader->parse($content) as $statement) {
    foreach ($statement->getOperations() as $operation) {
        echo "Date: " . $operation->getDate()->format('Y-m-d') . "\n";
        echo "Value Date: " . $operation->getValueDate()->format('Y-m-d') . "\n";
        echo "Amount: " . $operation->getAmount() . "\n";
        echo "Label: " . $operation->getLabel() . "\n";
        echo "Reference: " . $operation->getReference() . "\n";
        echo "Bank Code: " . $operation->getBankCode() . "\n";
        echo "Account: " . $operation->getAccountNumber() . "\n";

        // Optional fields are null when blank
        if (null !== $operation->getInternalCode()) {
            echo "Internal Code: " . $operation->getInternalCode() . "\n";
        }

        // Operation details (additional information)
        foreach ($operation->getDetails() as $detail) {
            echo "Additional Info: " . $detail->getAdditionalInformations() . "\n";
        }
    }
}
```

## Amounts

Balance and operation amounts are floats, signed: credits are positive, debits are negative. In the file, an amount is
13 digits and a sign character, which also holds the last digit; the number of decimals comes from position 20 of the
line:

| Last character | Sign     | Last digit |
| -------------- | -------- | ---------- |
| `{`, `A`…`I`   | positive | 0, 1…9     |
| `}`, `J`…`R`   | negative | 0, 1…9     |

`0000000166956E` with 2 decimals is `16695.65`, with 0 decimals `1669565`; `0000000000227R` with 2 decimals is
`-22.79`.

:::tip[Floats and money]
Add and compare `getAmountInMinorUnits()` (since 6.6) instead of the floats: the exact amount as an integer, `1669565`
for `16695.65` with 2 decimals, `getNumberOfDecimals()` giving the decimals. Converting a float yourself loses cents:
`(int) (0.29 * 100)` is `28`.
:::

## Dates

Dates are `DateTimeImmutable` objects at midnight, in the default time zone of PHP, read from `DDMMYY`: years `00` to
`69` are 2000 to 2069, `70` to `99` are 1970 to 1999.

A date that does not exist throws a `ParseException` instead of rolling over to the next month: day `00` or `32`, month
`00` or `13`, 31 April, 29 February of a non-leap year. `320420` fails with `Unable to parse date "320420"`.

Every CFONB 120 date is mandatory, the value date of an operation included. Some banks write a date they do not have
as zeros: `000000` fails with `Unable to parse date "000000": the date is zero-filled (empty), but this field is
mandatory`, in strict and non-strict mode alike.

:::note[Since 6.5]
6.4 read a zero-filled date as 30 November 1999, and a date that does not exist as a date of the next month, instead of
throwing.
:::

## Strict mode (default) vs non-strict mode

In strict mode, any line that cannot be parsed throws a `ParseException`. Non-strict mode only relaxes one rule: a blank
operation reference on a `04` line becomes an empty string instead of an error. Every other error is still thrown, the
[order of the records](#how-statements-are-built) and zero-filled [dates](#dates) included.

```php
use Silarhi\Cfonb\Cfonb120Reader;
use Silarhi\Cfonb\Exceptions\ParseException;

$reader = new Cfonb120Reader();

// Strict mode (default) - throws an exception on parsing errors
try {
    $statements = $reader->parse($content); // strict=true by default
} catch (ParseException $e) {
    echo "Parsing error: " . $e->getMessage() . "\n";
}

// Non-strict mode - blank operation references are returned as ''
$statements = $reader->parse($content, false); // strict=false
```
